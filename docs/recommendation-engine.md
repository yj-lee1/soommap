# 2단계 추천 엔진

## 범위와 경계

수동 입력 → 서버 조건 검증 → 기존 공개 데이터 캐시 → 순수 추천 함수 → 원래 계획과 비교 결과 순서다. OpenAI·새 유료 서비스·상시 프로세스를 추가하지 않는다. 이후 AI 해석은 같은 조건 검증과 엔진을 사용한다.

- `conditions.ts`: 알 수 없는 외부 입력을 검증하고 허용한 필드만 새 객체로 만든다.
- `manual.ts`: 한국 시간 입력을 UTC로 변환한다. ‘1시간 늦어도 됨’은 원래 시각부터 +60분까지이며 앞당기지 않는다. 자정을 넘어도 원래 계획은 유지한다.
- `recommend.ts`: 시각·자료·조건을 인자로 받는 결정적 함수. 서버·브라우저·AI·호스팅에 의존하지 않으며 입력을 수정하지 않는다.
- `/api/recommendations`: 최대 16KiB JSON, 조건 검증 후 자료 조회, 사용자별 조건·결과는 저장·캐시·로그에 남기지 않고 `no-store`로 반환한다.
- `manual-planner.tsx`: 편집한 조건과 적용 결과를 구분한다. 조건 변경 시 이전 결과를 숨기고 진행 중 요청을 취소한다. 버전이 지난 응답을 무시하며 실패해도 입력을 유지한다.
- `/data`: 1단계 원자료 표와 출처·기준 시각·수신 시각을 유지한다.

## 필수 조건과 순서

장소의 활동·환경, 허용 장소, 제외 장소, 장소 고정, 도착 범위, 시각 고정을 먼저 적용한다. 시간 범위는 양끝을 포함하며 최대 24시간이다. 이미 지난 도착 시각은 새 추천에서 제외한다. 필요한 허용 조건이 미정이면 확인을 요구하며, 허용 장소가 빈 배열이면 후보 없음으로 처리한다.

2026-09-17 사용자 보완 요청으로 [도착·체류 정렬 정책](temporal-alignment.md)을 적용했다. 17:30도 60분 이내 앞뒤 표본이 있으면 평가한다. 인구 범위만 숨맵 추정으로 보간하며 혼잡 단계는 보간하지 않는다. 체류시간이 있으면 종료까지의 표본·누락·변화를 함께 평가한다. 현재 관측으로 미래를 대체하거나 범위 밖을 외삽하지 않는다.

- 변경 최소: 평가 표본이 모두 선호 이내인 후보 안에서 변경 항목 수 → 장소 유지 → 시간 차이 절댓값 → 표본 중 가장 높은 혼잡 단계.
- 덜 붐빔 우선: 표본 중 가장 높은 혼잡 단계 → 변경 항목 수 → 장소 유지 → 시간 차이 절댓값.
- 선호 이내 표본으로 평가한 후보가 없으면 경계 표본이 선호를 넘나드는 후보를 `preference-uncertain`으로 표시한다. 이것도 없으면 필수 조건 안에서 낮은 표본 단계부터 `preference-unmet`로 보여준다.
- 기존 항목이 모두 같으면 동일 단계 표본을 우선하고 도착 시각·장소 ID로 동률을 고정한다. 실제 이동 부담이나 인구 감소율은 계산하지 않는다.

추천·다른 선택·원래 계획을 합쳐 최대 3장이다. 원래 계획이 추천이면 별도 원래 계획 카드를 중복하지 않는다. 원래 계획이 필수 조건 밖이면 `비교 제외` 참고 카드로만 표시하고 추천 ID나 대안 ID로 반환하지 않는다. `candidates`에는 화면에 표시할 원래 계획 참고 자료도 들어갈 수 있으므로, 이후 AI는 반드시 `recommendedCandidateId`, `alternativeCandidateIds`, `options[].eligible`을 구분해야 한다.

## 31분과 34분의 의미

실제 사용자 검수 화면에서 원자료 14:55, 확인 15:29, 34분 전을 확인했다. 이전 보고는 확인 시각 15:26이라 31분이었다. `floor((확인 시각 - 원자료 시각) / 60초)`이며 수신 시각과는 별개다. 열린 화면의 숫자가 매분 자동 변경되는 방식은 아니며 새로 확인·계산한 시점을 기준으로 한다.

## 지연 예측 정책

1단계의 관측 최신성 기준은 그대로 유지한다. 30분 이내 최근, 30분 초과~60분 지연, 60분 초과 오래된 자료다. 이는 내부 제품 기준이며 공식 정확도 보증이 아니다.

2단계에서는 **현재 관측을 최신으로 취급할지**와 **제공된 미래 예측을 참고 비교할지**를 구분한다. 30~60분 전 원자료의 미래 예측은 사용자가 `지연 예측 참고 비교를 허용해요`를 직접 선택해야 쓴다. 초기값은 허용하지 않음이다. 허용해도 관측 상태를 최근으로 바꾸지 않고 결과와 카드에 `지연 예측 참고`를 표시한다.

60분 초과, 대체 자료/대체 여부 미상, 10분 초과 새 수신 없음, 미래 예측 없음은 동의 여부와 관계없이 제외한다. 예측 생성 시각이 별도 제공됐다고 가정하지 않으며, 해당 예측이 포함된 응답의 원자료 기준 시각과 수신 시각을 근거로 표시한다. 도착 예측이 머무는 전 시간의 상태를 보장하지 않는다.

## 상태와 근거

| 상태 | 의미 |
|---|---|
| ready | 필수 조건·자료 검사를 통과하고 평가 표본이 모두 선호 이내인 후보 있음 |
| preference-uncertain | 방문 경계의 전후 표본이 선호 수준을 넘나들어 충족 단정 불가 |
| preference-unmet | 필수 조건을 지킨 후보는 있지만 혼잡 선호 미충족 |
| needs-clarification | 허용 장소 또는 시간 범위 미정 |
| no-candidates | 장소·활동·환경·제외·고정 조건을 함께 만족하는 장소 없음 |
| data-unavailable | 허용 장소는 있으나 쓸 수 있는 예측 자료 없음 |
| forecast-unavailable | 도착·체류 구간을 평가할 표본 부족 또는 표본 간격 60분 초과 |

각 후보는 장소·시각·도착 정렬·체류 평가·원자료/수신 시각·스냅샷 ID·실제 예측 표본의 evidence ID를 포함한다. 단일 `congestion` 필드를 제거하고 공식 표본과 자체 판정을 구분한다. 장소별 제외 이유를 제공한다. 부분 장애면 정상 장소로 비교한다. 선택 완료·복사·잠금 칩·두 진입 모드·자연어는 후속 단계다.

## 배포에서 발견한 첫 요청의 갱신 시차

첫 Preview의 15:47:01 추천은 이전 캐시(15:26 수신)로 보류됐지만, 같은 요청에서 시작한 원본 갱신은 15:47:02에 정상 완료됐다. 인증 오류나 서울시 장애가 아니었다. 표준 Data Cache의 stale-while-revalidate 동작 때문에 갱신 전 자료가 먼저 반환된 경우다.

캐시가 갱신 간격보다 오래됐으면 같은 worker에서 **이미 시작한 갱신 Promise**를 기다리도록 보완했다. 새 원본 호출은 추가하지 않고, 기존 8초 제한과 실패 시 마지막 정상값 반환을 유지한다. 다른 worker에서만 진행되는 갱신까지 기다리는 분산 락을 도입한 것은 아니다. [Next.js 캐시 설명](https://nextjs.org/docs/app/guides/caching-without-cache-components)

고정 자료 기반 62개 테스트(데이터 19개 + 추천 23개 + 시간 정렬·체류 20개). 추천 조합 검사는 허용 장소·장소 고정·시간 고정·혼잡 선호·정렬 모드의 288개 조합에서 필수 조건 위반과 중복 카드가 없는지 확인한다. 외부 API는 테스트에서 호출하지 않는다.

최초 2단계 검증 기록은 [보고](reviews/stage-2.md)에 보존한다. 당시 16:30 고정은 예측 없음이었지만, 보완 후에는 양쪽 표본이 있으면 자체 정렬로 평가한다. 추가 모의 HTTP·브라우저 검증은 [시간 정렬 문서](temporal-alignment.md)에 기록한다.
