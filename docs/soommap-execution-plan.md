## 1. 진행 원칙

**실제 데이터 → 추천 엔진 → 실제 AI → 조건 수정 → 부가 기능 → 디자인 일괄 적용 → 최종 검증·제출** 순서로 진행한다. 첫 검수 배포는 앞단에서 하고, 이후 같은 프로젝트에 기능을 더한다. 단계별 Preview URL은 각 보고에서 제공한다.

색상·서체·브랜드·아이콘·장식·모션은 뒤로 미룬다. 반면 입력 순서, 조건의 의미, 버튼 동작, 모바일에서 누를 수 있는지, 오류·빈 결과·로딩 표시는 기능 단계에 포함한다. 이 동작까지 뒤로 미루면 마지막에 화면과 추천 로직을 함께 고쳐야 한다.

각 단계는 ‘코드를 작성함’이 아니라 **브라우저에서 완료 조건을 확인함**으로 끝낸다. 개발 중 가상 자료를 사용하면 예시임을 표시하고, 제출 기능의 완료 판정은 실제 데이터·실제 AI 호출로 한다.

### 실행·검수 규칙

1. **단계 안에서는 자율 실행:** 승인된 범위의 구현, 디버깅, 테스트, 문서 정리와 검수용 결과 준비는 제가 진행한다. 함수·파일 구성 같은 통상적인 구현 선택을 매번 묻지 않는다.
2. **중간 요청은 필요한 항목만:** 계정 접근, 키 발급, 비용 한도, 제품 범위 변경, 사용자 선호 등 결정이 필요한 이유·추천안·영향을 함께 요청한다. 기다리는 동안 같은 단계 안의 독립 작업은 진행할 수 있다.
3. **검수 가능한 결과를 먼저 준비:** 자체 점검 후 링크·화면·예시 입력·변경 파일·커밋을 제공한다. 미완성 기능을 완료했다고 보고하지 않는다.
4. **단계 끝에서 승인 대기:** 사용자가 ‘승인/다음 단계 진행’ 또는 동등한 의사를 밝히기 전 다음 단계의 구현을 시작하지 않는다. 응답 지연이나 시간 경과는 승인으로 보지 않는다.
5. **수정 요청은 같은 단계에서 처리:** 의견을 반영하고 영향을 받는 동작을 다시 확인한 뒤 재검수를 요청한다. 완료와 사용자 검수 완료를 구분해 기록한다.
6. **단독 작업:** 다른 개발자나 별도 에이전트에 구현을 분담하지 않는다. 사용자에게 개발 작업을 배정하지 않고, 필요한 판단·계정 작업·실사용 확인만 요청한다.
7. **일정 변경도 보고:** 검수 대기나 연동 문제로 목표가 밀리면 완료한 결과와 축소 가능한 범위를 제시한다. 승인 단계를 임의로 생략하지 않는다.

### 저장소 운영

- 0단계에서 원격 저장소 접근·기본 브랜치·기존 파일·이력을 먼저 확인한다. 현재 로컬 문서와 원격 작업을 보존하고 기존 이력을 이어서 작업한다.
- 기존 저장소 정책이 있으면 따른다. 초기에는 `codex/soommap-build`를 사용했고, 사용자 지시로 1단계부터 `feat/hangang-data-foundation` 등 표준 기능별 이름을 사용한다.
- `.env`·키·개인 정보·불필요한 첨부파일을 제외하고 관련 파일만 커밋한다. 사용자 변경을 되돌리거나 원격 이력을 강제로 덮어쓰지 않는다.
- 단계별로 검수 가능한 커밋을 남기고 지정 작업 브랜치에 반영한다. GitHub 반영 여부·커밋 ID와 검수용 배포가 같은 버전인지 보고한다. 원격 권한 문제면 로컬 완료와 원격 미반영을 구분한다.
- 기본 브랜치 반영과 최종 서비스 공개는 7단계의 완성본 검수에서 구체적으로 승인받은 범위로 8단계에서 수행한다. 같은 조치에 대한 승인을 다시 묻지 않는다.

## 2. 단계별 작업표

| 단계 | 만들 결과 | 주요 작업 | 다음 단계로 넘어가는 기준 |
|---|---|---|---|
| 0. 저장소·환경·연동 확인 | 실제 연동 가능성이 확인된 빈 서비스 | 지정 원격 연결, 계정·키, 프로젝트, API 시험 호출, 검수용 첫 배포 | 작업 브랜치·배포 서버에서 서울 데이터와 AI 인증·응답 확인 |
| 1. 데이터 기반 | 검증된 장소 목록과 최신 데이터 | 일반 Place 모델, 한강 5곳, 예측 정규화, 캐시·결측·시각 | 공원별 실제 값과 비교 가능한 예측 시각 확인 |
| 2. 추천 엔진 | 수동 입력으로 작동하는 추천 | 조건 모델, 후보 생성, 필터, 정렬, 기준 계획·변경 내역 | 같은 조건·자료에 같은 결과, 고정 조건 위반 없음 |
| 3. AI 연결 | 말로 시작할 수 있는 기능판 | 자연어 해석, 모호한 조건 확인, 설명·근거 검증, 실패 대체 | 자연어 → 조건 → 실제 후보 → 이유가 공개 URL에서 연결 |

| 6. 디자인 통합 | 하나의 제품처럼 보이는 화면 | 색·서체·간격·카드·조건 표시·지도 스타일·최소 모션 | 모바일·데스크톱에서 같은 기능과 상태 유지 |
| 7. 최종 검증·제출 준비 | 사용자가 승인할 완성본 | 사용자 관찰, 모바일·장애 확인, 운영 설정, 시연·제출 문구 | 실제 서비스와 제출 자료가 일치하는 완성본 검수 |
| 8. 최종 반영·제출 확인 | 제출·운영 상태 확인 | 승인된 버전 최종 반영, 제출 지원, 완료·복구 정보 정리 | 최종 URL·버전·제출 완료 상태 확인 |

0~4단계가 제품의 중심이다. 5단계의 모든 항목이 끝나야 6단계를 시작하는 구조로 만들지 않는다. 기능 동결 시각에 통과한 기능을 대상으로 디자인을 적용한다.

완료 기준: 수동 조건을 바꾸면 실제 자료로 결과가 계산된다. ‘한 시간 늦춰도 됨’에서 앞당긴 후보가 나오지 않는다. 원래 계획은 후보 선택으로 덮어쓰지 않는다. 혼잡 선호를 바꿔도 반드시 지킬 조건은 유지된다.

필터·정렬·시간 계산은 독립된 로직으로 두고 화면 컴포넌트 안에 넣지 않는다. 체류시간은 표시하되 도착 예측으로 체류 전체의 혼잡을 보장하지 않는다.

## 6. 3단계 — 자연어와 AI 설명 연결

- [ ] 자연어에서 활동, 기준 계획, 허용 범위, 고정 조건, 혼잡 선호 추출.
- [ ] AI 결과를 서버에서 검증한 뒤 2단계와 같은 조건 모델에 전달.
- [ ] 중요한 미정 조건만 짧게 확인하고, 해석한 조건은 직접 수정 가능하게 표시.
- [ ] 후보·근거 목록 안에서 추천·제외 이유와 절충점 설명.
- [ ] 시각·혼잡·장소 등 사실값은 데이터에서 표시. 없는 장소·이동시간·소음 수치 생성 차단.
- [ ] 해석 실패는 입력을 보존한 수동 폼, 설명 실패는 검증된 결과와 기본 문장으로 대체.
- [ ] 요청 길이·호출 빈도·사용량 상한, 서버 키 관리 적용.

완료 기준: 공개 URL에서 실제 AI로 요청 하나를 해석해 실제 데이터 추천을 받는다. 명확한 요청은 불필요한 추가 확인 없이 진행하고, AI가 지원하지 않는 조건을 충족한 것처럼 말하지 않는다.

버튼으로 바꾼 조건은 직접 엔진에 전달한다. 매번 원문 전체를 AI가 다시 읽게 하지 않는다. 자유문장으로 조건을 정정하는 확장은 버튼 재추천이 안정된 뒤 연결한다.

## 7. 4단계 — 핵심 체험을 끝까지 연결

아래 순서로 기능을 더한다. 기존 상태와 계산을 재사용해 새로운 기능마다 별도 엔진을 만들지 않는다.

- [ ] `17시 고정`·`여의도 고정`과 해제. 해제하면 이전에 허용한 범위로 복원.
- [ ] ‘갈 수 있는 공원’ 선택. 선택 범위 밖 장소는 추천하지 않음.
- [ ] 목적지 있음/미정의 두 시작 방식. 미정이면 원래 계획 대신 처음 정한 조건 표시.
- [ ] 미정 시각 처리: ‘19시 이후’는 하한, ‘오늘 저녁’은 확인 또는 명시된 제안 범위. 데이터 범위와 사용자 허용 범위 분리.
- [ ] ‘이번에는 이곳 제외’와 복원. 허용 후보 선택의 지름길로 구현.
- [ ] 조건 충돌 안내와 완화 제안. 사용자가 선택하기 전 고정 조건을 풀지 않음.
- [ ] 추천에서 실제로 바뀐 항목 표시. 기존 결과와 새 조건을 혼동하지 않음.
- [ ] 연속 변경 시 최신 요청 결과만 반영. 이전 결과는 갱신 중 상태로 구분.
- [ ] 계획 선택 → 선택 요약 → 문구 복사·지도 위치 링크 → 다시 조정.
- [ ] 선택한 계획의 데이터 다시 확인. 갱신돼도 선택 자체를 임의로 바꾸지 않음.
- [ ] 한국어 정정 문장 연결: “망원은 빼줘”, “그럼 시간만 늦추자” 등. 버튼과 같은 조건 검증 적용.

‘선택한 계획을 새 기준으로 삼기’는 이번 우선순위를 낮춘다. 선택만으로 기존 기준을 자동 갱신하지 않는다. 예약·메시지 자동 전송·공동 편집은 포함하지 않는다.

완료 기준: 목적지 있음은 `요청 → 비교 → 고정 → 해제 → 선택`, 목적지 미정은 `요청 → 조건 확인 → 첫 추천 → 제외 → 재추천 → 선택`이 이어진다. 제외 후 후보가 없으면 이를 알리고 복원할 수 있다.

## 8. 5단계 — 기능을 넓히는 순서

| 순서 | 기능 | 이번 구현 범위 | 공개 조건 |
|---|---|---|---|
| 1 | 예측 그래프 | 선택 시각 주변과 제공 범위 최대 12시간, 이산 단계·결측 표시 | 실제 반환 시각만 사용, 과거·표본 사이 상태를 생성하지 않음 |
| 2 | 2D 지도 | 위치·집계 범위·카드 선택 연결, 모바일에서 펼치기 | 타일 조건·키 확인, 지도 실패 시 카드 기능 유지 |
| 3 | 기본 PWA | manifest·실행 설정, 임시 아이콘 | URL 사용이 기본이며 설치로 시작을 막지 않음 |
| 4 | 날씨·행사·공식 안내 | 통합 응답에서 바로 얻는 참고 카드와 출처 링크 | 대상 시각 구분, 행사와 혼잡의 인과관계 단정 안 함 |
| 5 | 장소 확장 | 비교 그룹을 먼저 정의하고 검증된 같은 유형 장소 추가 | 코드·영역·활동·예측·캐시 확인 완료, 개수 목표 강제 안 함 |
| 6 | 체류 구간 참고 | 구간 안에 실제 제공된 예측 표본 보여주기 | 계속 한산하다는 보장이나 임의의 평균 점수 없음 |

새 장소 추가를 위해 새로운 API 체계·별도 추천 정책이 필요하면 제출 이후로 넘긴다. 출발지 기반 실제 이동시간, 지하철 혼잡, 동행자 조율, 알림·로그인, 자체 예측, 과거 패턴은 후속 개발 목록이다.

3D는 별도 조건부 항목이다. 기능 동결 전에 기존 타일의 필요한 값·이용 조건·표시 동작·성능까지 확인한 경우에만 공개한다. 디자인 단계에서는 이미 작동하는 표현의 스타일만 다듬는다. 동결 이후 새로운 3D 기능이나 별도 도시 모델을 만들지 않는다.

## 9. 6단계 — 디자인을 한 번에 적용

디자인 시작 전 기능 목록을 동결하고 통과한 버전을 남긴다. 불완전한 선택 기능은 공개 화면에서 숨긴다. 핵심 흐름이 실패한 상태라면 부가 기능부터 제외하고 기능을 복구한다.

### 기능 단계에서 이미 갖출 것

- 한 화면의 순서: 입력 → 조건 → 추천 → 수정 → 다른 선택 → 근거·지도 → 선택 완료.
- 목적지 유무에 따른 카드 구성, 값이 드러나는 고정 버튼, 변경 내역.
- 모바일 좁은 화면에서도 사용 가능한 기본 배치·입력·버튼.
- 로딩·정상·빈 결과·오류·오래된 자료 상태, 키보드 조작과 읽을 수 있는 라벨.
- 화면 표시 데이터와 이벤트 인터페이스 분리. 디자인 변경은 동일 동작에 적용.

### 이 단계에서 일괄 적용할 것

- [ ] 색상·서체·글자 크기·간격·모서리·그림자 기준 통일.
- [ ] 입력창, 조건 칩, 잠금·제외·복원 버튼, 추천·비교 카드 스타일.
- [ ] 유지/변경/미확인 내용의 위계, 현재/예측/지연 라벨.
- [ ] 모바일 지도 펼치기·상세 영역, 데스크톱 지도·플래너 배치 다듬기.
- [ ] 그래프·지도·상태 메시지의 스타일 통일.
- [ ] 앱 아이콘·대표 이미지·공유 미리보기 이미지.
- [ ] 짧은 결과 전환과 모션 감소 설정. 필요할 때만 검증된 장소 이미지 사용.

약 2~3시간을 예약하는 목표이며 결과를 보장하는 견적은 아니다. 적용 순서는 기본 스타일 → 주요 컴포넌트 → 각 상태와 모바일 → 이미지·최소 모션이다. 추천 규칙이나 상태 모델을 다시 설계하는 시간을 이 단계에 섞지 않는다.

완료 기준: 기능판과 같은 요청에서 같은 조건·추천 결과가 나오고, 바뀐 부분과 다음 행동을 쉽게 읽을 수 있다. CSS 변경 후 작은 화면·키보드·대비·버튼 가림을 다시 확인한다.

## 10. 7단계 — 최종 검증·제출 준비

검증은 앞 단계부터 수행하며, 이 단계에서는 디자인과 배포 변경 이후의 전체 흐름을 확인한다.

- [ ] 실제 AI 평가 문장 10~15개: 시간 고정, 늦추기만 허용, 미정, 정정, 지원 외 요청, 충돌.
- [ ] 모바일·데스크톱 새 브라우저에서 첫 추천부터 선택 완료까지 확인.
- [ ] AI 실패·공공 데이터 실패·지도 실패·오래된 데이터·연속 수정 확인.
- [ ] 가능하면 실제 사용자 3명 내외 관찰: 결정 시간, 조건 누락, 변경 이해, 실제 갈 수 있는 안인지 기록.
- [ ] 사용자 모집이 되지 않았다면 내부 점검과 실제 사용자 검증을 구분해 제출. 효과 수치를 만들지 않음.
- [ ] 공개 서버의 키·캐시·사용량 제한·비용·운영 기간 확인. 개인 노트북 종료와 무관하게 사용 가능해야 함.
- [ ] 오류 시 복구 절차와 마지막 정상 배포로 돌아가는 방법 기록.
- [ ] 실제 동작하는 기능에 맞춰 문제·AI 역할·사용 도구·현재 범위·출처·한계 작성.
- [ ] 대표 이미지와 60초 시연 준비. 저장 예시는 실시간 상태와 구분.
- [ ] 서비스 링크 접속, 제출할 문구·이미지·시연·도구 목록을 한 묶음으로 준비.
- [ ] 사용자가 완성본을 검수할 수 있게 제공하고, 최종 반영·배포 범위를 구체적으로 제시해 승인 요청.

사용자 관찰을 할 사람은 개발과 별개로 미리 확보하는 편이 좋다. 가능하면 기능판에서 한 명에게 짧게 사용해 보게 해 큰 구조 문제를 디자인 전에 확인한다. 본 작업 계획 작성 중에는 누구에게도 연락하지 않았으며, 외부 연락은 별도 요청 없이 수행하지 않는다.

### 8단계 — 최종 반영·제출 완료 확인

- [ ] 7단계에서 승인한 버전을 지정한 기본 브랜치·최종 배포에 반영. 승인 범위에 없는 별도 변경을 섞지 않음.
- [ ] 최종 URL에서 비로그인 상태로 핵심 여정과 실제 데이터·AI 연결 재확인.
- [ ] 참가 신청·개인 정보·약관 확인처럼 사용자 본인의 판단·인증이 필요한 작업은 사용자에게 요청.
- [ ] 제출 자료를 바로 옮길 수 있는 형태로 제공. 최종 제출은 사용자 수행을 기본으로 하며, 명시적으로 대행을 요청한 경우 승인한 범위에서 지원.
- [ ] 실제 제출 완료 상태를 확인. 보지 못했으면 사용자 확인이 필요한 상태로 남기고 완료로 기록하지 않음.
- [ ] 배포 URL·커밋·설정 위치·운영 기간·오류 복구 방법을 인계 문서에 정리.
- [ ] 최종 결과를 보고하고 사용자의 최종 검수 요청.

제출 이후 지속 감시·자동 알림은 현재 계획에 포함하지 않는다. 별도로 요청하면 운영 방식과 알림 조건을 정한다.

| 동결 전 여유 있을 때 | 자유문장 정정의 범위 확대, 선택 계획 재확인 편의, 날씨·행사 참고, 추가 장소 그룹, 체류 표본 참고 |
| 이후 | 실제 경로·교통 혼잡, 여러 동행자 조율, 로그인·알림·이력 학습, 자체 예측, 정밀 3D |

일정이 밀리면 새 장소·새 활동·3D → 날씨·행사·체류 확장 → 자연어 정정의 추가 사례·재확인 편의 → 지도·PWA 장식 → 그래도 필요하면 목적지 미정 등 새 진입 순으로 줄인다. 지도 연동 자체가 막히면 검증된 외부 지도 링크로 축소하고, 설치 기능이 막히면 일반 웹 사용을 유지한다. 공개한 기능의 조건 검증·출처·오류 표시를 없애서 기능 수를 유지하지 않는다.

## 13. 사람의 개입을 요청할 시점

| 시점 | 제가 먼저 할 일 | 필요할 때 요청할 내용 |
|---|---|---|
| 0단계 | 기존 연결·권한·설정 확인, 필요한 항목만 정리 | GitHub SSH 인증, 서울 API 발급·설정, AI 공급자·모델과 사용 예산, 호스팅 선택·로그인 |
| 1단계 | 실제 가능한 장소·예측을 검사하고 대안을 제시 | 원래 5곳을 확보할 수 없을 때 지원 범위 변경 |
| 2~4단계 | 예시와 실제 결과로 추천 정책·동작을 보여줌 | 변경 최소 정책, 두 시작 방식, 문구·동작에 대한 사용감 |
| 5단계 | 완성된 부가 기능과 추가 가능한 범위·시간을 제시 | 새 장소 포함 여부, 디자인에 들어갈 최종 기능 목록 |
| 6단계 진입 전 | 차분한 색감·비교 카드 중심의 기본 시각 방향을 간단히 제시 | 강한 선호가 있을 때 색·분위기·브랜드 의견. 5단계 검수와 함께 받음 |
| 6단계 종료 | 모바일·데스크톱 화면과 동작을 준비 | 시각적 완성도와 읽기 편한지 검수 |
| 7단계 | 체험 링크·질문·기록 양식·최종 제출 자료 준비 | 실제 사용자 체험 도움, 제출 내용과 최종 반영 승인 |
| 8단계 | 승인한 버전 반영, 제출 자료·확인 절차 제공 | 본인 인증·약관·최종 제출·완료 상태 확인 |

키 자체를 채팅에 붙여 달라고 하지 않는다. 설정할 환경변수 이름·설정 위치를 제공하고 사용자가 입력할 수 있게 한다. 새 유료 결제나 상한 확대가 필요하면 비용과 대안을 먼저 제시한다. 이미 승인한 선택·비용 범위는 다시 묻지 않는다.

## 14. 단계별 보고와 검수 요청

각 보고에는 **완료한 것 / 확인한 결과 / 확인할 링크·버전 / 남은 제한 / 사용자가 볼 항목 / 다음 단계**를 담는다. 단순히 ‘잘 되나요?’라고 묻지 않고 짧은 검수 행동을 제공한다.

| 단계 | 제가 제공할 검수 자료 | 사용자가 확인할 핵심 |
|---|---|---|
| 계획 | 이 실행 계획과 진행 기록 | 단계·개입 시점·승인 방식이 원하는지 |
| 0 | 저장소·브랜치·커밋, 검수 URL, 비밀값 없는 연동 결과 | 지정 저장소 사용, 비용·호스팅 선택, URL 접속 |
| 1 | 5곳 데이터 표, 출처·시각·예측 가용 상태 | 지원 장소와 데이터 제한 수용 여부 |
| 2 | 수동 입력 화면, 대표 비교 2~3건, 조건 검증 결과 | 장소·시간 변경의 우선순위가 납득되는지 |
| 3 | 자연어 예시·해석·추천 결과·실패 대체 | 자신의 말이 올바르게 해석되고 설명되는지 |
| 4 | 두 진입 시나리오, 고정·해제·제외·선택 체험 | 처음부터 계획 선택까지 막힘 없이 쓸 수 있는지 |
| 5 | 동작하는 그래프·지도·PWA와 추가 정보, 포함/보류 목록 | 기능 범위를 확정하고 디자인 단계로 갈지 |
| 6 | 모바일·데스크톱 화면·URL, 디자인 전후 기능 확인 | 비교·수정이 잘 읽히고 전체 인상이 맞는지 |
| 7 | 최종 검증 결과, 시연·제출 자료, 남은 제한 | 완성본과 최종 반영·배포 범위 승인 |
| 8 | 최종 URL·커밋·제출 상태·운영 인계 | 실제 제출 완료와 결과물 최종 검수 |

응답 예시: `승인, 다음 단계 진행` / `수정: …` / `보류`. 부분 승인이라면 승인한 부분과 미해결 항목을 따로 기록하고 필요한 부분만 명확히 확인한다.

진행 기록의 상태는 `대기 → 진행 중 → 자체 확인 완료·검수 대기 → 승인 완료`로 관리한다. 수정 요청이면 `수정 중`으로 돌아간다. 단계 시작·완료·검수 응답의 날짜와 핵심 내용을 기록한다.

**2026-09-17 사용자가 이 계획을 승인했다. 0단계 검수 후 사용자가 1단계 착수를 승인했다. 사용자가 1단계를 승인하고 2단계 착수를 지시했다. 2단계 구현·최종 검수 배포·자체 검증을 완료하고 사용자 검수를 요청한다. 3단계 이후는 승인 전이다.**
