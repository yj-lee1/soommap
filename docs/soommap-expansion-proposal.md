# 숨맵 — 두 가지 시작 방식과 서울 장소 확장 보완안

작성: 2026-09-17 · 상태: 검토 제안 · 구현 전 · 기존 v2 기획과 수상 검토 문서는 그대로 보존

사용자가 제안한 ‘한강 5곳 우선 완성, 일반 Place 구조, 목적지 미정 지원, 서울 주요 장소 확장, 교통을 변경 부담으로 반영’을 검토했다. [기존 기획](./soommap-hackathon-plan.md), [수상·사용자 니즈 검토](./soommap-award-review.md)를 대체하지 않는다. 이 문서의 추가 범위는 권고이며 실제 API 연동·사용자 검증·배포 결과가 아니다.

## 1. 권고하는 제품 방향

**숨맵: 내 조건을 지키며 덜 붐비는 외출 계획을 찾고 조정하는 AI.**

장기 범위는 서울의 외출이고, 첫 공개 범위는 한강공원 5곳의 산책이다. 지원 장소·활동을 늘리는 구조는 준비하되 화면에는 실제 가능한 범위만 보여준다.

추가안에서 가장 가치 있는 것은 ‘아직 갈 곳을 정하지 않은 사람’도 같은 화면에서 시작할 수 있다는 점이다. 기존의 최소 변경 재계획을 유지하면서, 첫 계획을 찾는 진입을 더할 수 있다. 장소 수 확대가 AI 활용의 깊이나 사용자 효용을 자동으로 높이는 것은 아니다.

| 제안 | 판단 | 보완할 부분 |
|---|---|---|
| 한강 5곳을 먼저 완성 | 유지 | 실제 응답·조건 수정·공개 배포·사용자 관찰이 먼저 |
| 일반 Place 모델 | 처음부터 적용 | 정적 장소 목록과 데이터 공급자 연결을 분리하는 정도로 시작 |
| 목적지 미정 시작 | 다음 기능으로 우선 검토 | 원래 계획이 없을 때의 정렬·표현을 별도로 정의 |
| 활동별 유사 장소 비교 | 장소 추가보다 먼저 정의 | 산책 태그 외에 강변 등 사용자가 요구한 환경도 유지 |
| 서울 장소 5~10곳 추가 | 검증 통과 후 조건부 | 개수 목표보다 활동 적합성·영역·예측 가용성 검사가 우선 |
| 출발 위치 | 실제 쓰임이 준비된 뒤 | 초기에는 갈 수 있는 공원 선택으로 대응 |
| 실제 이동시간·교통 혼잡 | 후속 | 출발·도착·교통수단·시각·경로 데이터가 필요 |

## 2. 첫 화면: 한 페이지에서 두 가지 시작

첫 화면 문구 제안:

> 오늘은, 덜 붐비는 쪽으로.
>
> 내 조건에 맞는 외출 계획을 찾고 조정해요.
>
> 현재 한강공원 5곳의 산책을 비교할 수 있어요.

입력창 위에 `갈 곳이 있어요 / 아직 못 정했어요`라는 작은 전환을 둔다. 별도의 필수 선택 페이지나 탐색 피드를 만들지 않는다. 사용자의 자연어로 이미 의도가 분명하면 그에 맞게 요약한다. 전환은 입력 예시를 돕는 장치이며 입력한 조건을 지우지 않는다.

| 시작 | 입력 예시 | 결과의 초점 |
|---|---|---|
| 갈 곳이 있어요 | “오늘 17시 여의도에서 걷고 싶어. 18시까지 늦출 수 있고 망원도 괜찮아.” | 원래 계획과 실제 바뀌는 항목 비교 |
| 아직 못 정했어요 | “오늘 19시 이후 한강에서 걷고 싶어. 여의도나 망원이면 좋아.” | 가능한 장소·시각 중 조건에 맞는 첫 계획 |

첫 버전에는 여러 활동의 버튼을 전부 노출하지 않는다. 산책만 지원하면서 ‘문화생활·놀러가기’를 실행 가능한 기능처럼 보이면 오히려 범위를 오해하게 한다. 또한 ‘산책’은 활동, ‘도심’은 환경, ‘데이트’는 동행 상황이므로 같은 분류 축에 섞지 않는다.

목적지 미정 결과는 추천 1개와 다른 선택 최대 1개, 처음 정한 조건 요약으로 충분하다. 가상의 원래 목적지를 만들어 세 카드를 채우지 않는다. 지도는 위치를 확인하는 보조 영역으로 유지한다.

## 3. 두 시작 방식을 연결하는 규칙

### 기준 계획은 일부만 정해져 있을 수 있다

- “19시에는 꼭 가야 하고 장소는 미정”이면 장소 기준은 없고 19시는 고정 조건이다.
- “19시가 좋지만 20시도 가능”이면 19시는 희망 기준이며 허용 범위는 별도다.
- “19시 이후”이면 19시는 시간 범위의 시작이다. 20시 추천을 ‘1시간 늦춤’이라고 쓰지 않는다.
- “오늘 저녁”은 특정 시각이 아니다. 필요한 경우 한 번의 시간 선택으로 확인하거나, 제품이 제안하는 범위임을 표시하고 수정할 수 있게 한다.

**이미 정한 항목에만 변경을 계산한다.** 장소가 미정이면 새 장소는 ‘선택’이지 ‘변경’이 아니다. 시간도 범위만 주어졌으면 가상의 기준 시각을 만들지 않는다.

### 후보 계산은 공유하고 정렬의 의미를 구분한다

공통 단계는 `활동·환경 적합성 → 갈 수 있는 장소 → 허용 도착 시각·고정 조건 → 해당 시각의 유효한 예측`이다.

- 기존 계획이 있으면 기존 v2의 변경 최소/혼잡 우선 정책을 적용하되, 기준이 있는 항목만 변경 비용에 포함한다.
- 장소·시각 모두 미정이면 조건을 만족하는 후보의 서울시 혼잡 예보를 비교한다. 동률은 이른 도착 시각과 안정적인 장소 순서 등 공개된 기본 규칙으로 처리한다. 사용자에게 더 가깝거나 더 좋은 장소임을 뜻하지 않는다.
- 목적지 미정이라고 사용자 범위 밖 장소·시각을 허용하지 않는다. 최신 예측이 없으면 임의의 값을 만들지 않는다.
- 사용자의 허용 시간과 데이터가 있는 시간을 따로 유지한다. 예측이 21시까지만 있어도 ‘사용자는 21시까지 가능’으로 바꾸지 않고 ‘현재 비교 가능 범위가 21시까지’라고 설명한다.

### 선택·고정·기준 변경은 구분한다

추천 카드를 열거나 계획을 선택하는 동작은 `selectedPlan`을 바꾼다. 기존 원래 계획을 자동으로 덮어쓰지 않는다. 새로운 기준을 만들고 싶다면 ‘이 계획을 기준으로 조정’처럼 의미가 드러나는 행동으로 설정하고 초기 요청은 보존한다. 해당 전환을 이번에 구현하지 못하면 선택·고정·재추천만으로 끝내도 된다.

목적지가 미정일 때 ‘장소 유지’ 버튼은 의미가 없으므로, 추천 이후 `망원으로 고정`, `19시로 고정`처럼 값을 명시한다. 고정 해제는 이전 허용 범위로 돌아간다. 화면의 시작 방식 전환과 ‘변경 최소/덜 붐빔 우선’ 정렬 전환을 같은 상태값으로 관리하지 않는다.

‘조용한 곳’이라는 요청은 소음 조건을 포함할 수 있다. 혼잡 회피로 해석한 부분을 보여주고 소음은 확인하지 못한다고 짧게 안내한다. 소음 요구를 충족했다고 설명하거나 조용함을 검증된 장소 특성으로 저장하지 않는다.

## 4. 장소 확장 전에 필요한 분류

`walk` 하나만으로 강변, 상권 골목, 궁궐을 동등한 대안으로 만들지 않는다. 최소한 다음을 나눈다.

| 구분 | 예시 | 쓰임 |
|---|---|---|
| 활동 | 산책 | 무엇을 하려는지 |
| 환경 | 강변, 공원 | 요구한 경험을 유지하는지 |
| 비교 그룹 | 한강 산책, 도시 공원 산책 | 운영자가 검토한 대안 묶음 |
| 사용자 허용 범위 | 여의도·망원 | 이번 계획에서 실제 갈 수 있는 곳 |
| 특정 대상 | 특정 공연·행사·약속 장소 | 다른 곳으로 바꾸면 목적이 사라지는 조건 |

활동·환경 정보는 검증된 장소 목록에서 제공한다. LLM이 매 요청마다 ‘데이트 명소’, ‘조용한 공원’ 등의 속성을 만들어 후보를 늘리지 않는다. 활동 태그와 운영자가 만든 그룹은 추천 정책이며 공식 혼잡 API가 제공한 평가로 표시하지 않는다.

서울시는 주요 121곳의 도시데이터를 제공한다. 이는 서울 모든 장소나 개별 가게를 포괄한다는 뜻이 아니다. 넓은 권역의 혼잡도를 해당 권역 안 카페 좌석이나 산책로 한 구간의 혼잡도로 옮겨 쓰지 않는다. [서울시 안내·FAQ](https://data.seoul.go.kr/dataVisual/seoul/guide.do)

**장소 확장보다 분류가 먼저**다. 기존 제안의 ‘10~20곳 추가 → 활동 그룹’ 순서를 ‘활동·환경·비교 그룹 정의 → 검증된 장소 추가’로 바꾸는 편이 맞다.

## 5. 작은 확장 구조

첫 버전은 정적 설정 파일과 최신 데이터 저장 구조로도 충분하다. 별도의 장소 관리 화면이나 여러 분류 테이블을 먼저 만들 필요는 없다. 아래는 모델의 방향을 설명하는 예시이며 구현한 코드가 아니다.

```typescript
type Place = {
  id: string;
  name: string;
  source: { provider: "seoul-city"; areaCode: string };
  groupIds: string[];
  activities: string[];
  settings: string[];
  displayPoint: { latitude: number; longitude: number };
  boundaryRef: string;
  enabled: boolean;
};
```

- `id`는 다섯 공원 이름을 엔진 곳곳에 박아 넣는 방식 대신 목록에서 읽는다. 활동·단계처럼 제한된 값에는 타입과 검증을 사용해도 좋다.
- `groupIds`는 복수 소속을 허용한다. 하나의 장소는 서로 다른 검증된 비교 그룹에 포함될 수 있다.
- `displayPoint`는 지도 표시 지점이다. 실제 입구·만남 지점·교통 목적지 좌표로 자동 사용하지 않는다.
- `boundaryRef`는 공식 집계 영역과 연결한다. 장소가 넓을 때 지도와 설명에 범위를 보여준다.
- `enabled`는 서비스에서 공개하기로 검토한 장소라는 뜻이다. 오늘 특정 시간의 데이터가 유효하다는 뜻은 아니다.
- 현재 관측·예측 목록·대체 여부·원자료 시각은 별도의 스냅샷에 둔다. 예측 제공 여부를 영구적인 장소 속성으로 고정하지 않는다.
- 이번 목록의 활동·환경·그룹 값은 허용된 값 집합으로 검사한다. 자유 문자열을 LLM이 생성해 분류를 확장하지 않는다.

추천 흐름은 `장소 목록 → 데이터 정규화 → 후보 필터 → 정렬 → 설명`으로 분리한다. 같은 데이터 공급자·같은 추천 정책 안의 장소 추가는 설정 중심으로 처리할 수 있다. 새로운 활동·교통 공급자·영업시간·시설 조건까지 코드 변경 없이 해결된다고 약속하지 않는다.

## 6. 같은 API여도 확인할 사항

공식 매뉴얼의 혼잡 등급은 장소별 과거 인구, 면적 대비 밀집도와 장소 특성 등을 반영한다. 같은 등급이 장소 간 동일한 절대 인원·밀도를 뜻하지 않는다. **‘서울시 혼잡 예보가 더 낮은 후보’**로 설명하고, 등급 차이를 사람 수 감소율·소음·안전성으로 환산하지 않는다. [서울시 도시데이터 매뉴얼](https://data.seoul.go.kr/SeoulRtd/downloads/%EC%8B%A4%EC%8B%9C%EA%B0%84_%EB%8F%84%EC%8B%9C%EB%8D%B0%EC%9D%B4%ED%84%B0_%EB%A7%A4%EB%89%B4%EC%96%BC.pdf)

장소를 공개 후보로 추가할 때 확인할 조건:

1. 공식 장소 코드와 집계 영역을 연결했다.
2. 해당 활동·환경이 실제 목적에 맞는지 검토했다.
3. 인증키로 현재값과 예측 제공 여부·시각을 확인했다.
4. 비교할 방문 시각에 실제 예측이 있는 후보가 있다.
5. 미제공·오래된 자료·대체 자료 상태가 표시된다.
6. 추가 호출량·캐시·모바일 목록이 감당할 수 있다.

2025년 공식 확대 공지는 예측 120곳을 명시한다. 현재 121곳 모두 항상 같은 길이의 예측을 제공한다고 가정하지 않는다. `FCST_YN`과 반환된 시각 배열을 기준으로 동작해야 한다. 실제 장소별 응답은 아직 확인하지 않았다. [확대 공지](https://data.seoul.go.kr/together/notice/datasetNoticeView.do?bbsCd=10008&seq=27399e1302ead42db866fa14824c4c56), [인구 API](https://data.seoul.go.kr/dataList/OA-21778/A/1/datasetView.do)

한 장소당 한 호출로 5분마다 하루 종일 수집한다고 가정하면 5곳은 1,440회, 15곳은 4,320회, 121곳은 34,848회다. 이는 계산이며 실제 허용량이나 현 기본 캐시의 호출 수가 아니다. 목록을 확장했다고 121곳을 매 사용자 요청마다 조회하지 않는다.

## 7. 이동 부담을 반영하는 순서

초기에는 ‘이번에 갈 수 있는 공원’을 직접 고르게 한다. 출발지를 입력해도 실제 경로나 검증된 권역 규칙에 쓰지 않는다면 입력 부담만 늘어난다. 위치 권한도 필수로 요구할 필요가 없다.

후속 이동시간 비교에는 출발 지점, 교통수단, 계획 시각, 실제 도착 지점이 필요하다. 공원 중심 좌표나 직선거리만으로 ‘11분’, ‘더 가까움’, ‘작은 변경’이라고 표시하지 않는다. 실제 경로 데이터가 생기면 기존 목적지까지의 시간과 대안까지의 차이를 비교하는 방식이 적절하다.

사용자가 인용한 1~8호선 자료와 9호선 자료는 30분 구간 통과 열차의 평균 혼잡도다. 각각 분기별·연간 갱신 자료로 설명되며, 현재 역사 안의 인파나 지금 열차 상태와 구분해야 한다. 향후 쓸 때도 ‘평소 시간대 평균’ 등 기준을 표시한다. 모든 교통 데이터가 실시간이 아니라는 포괄적 주장으로 확장하지 않는다. [1~8호선 공식 설명](https://data.seoul.go.kr/bsp/wgs/dataView/data300View/645.do), [9호선 데이터](https://data.seoul.go.kr/dataList/OA-22197/F/1/datasetView.do)

## 8. 추가 아이디어 한 개: 이번에는 이곳 제외

새 외부 데이터 없이 두 시작 방식 모두에 도움이 되는 후보는 추천 카드의 **‘이번에는 이곳 제외’**다. 별도 선호 학습이나 영구 프로필을 만들지 않고 현재 계획에만 적용한다.

> “망원은 이번에 빼줘.”
>
> “망원을 제외했어요. 19시 이후·한강 산책 조건은 유지했어요.”

‘너무 멀어요’를 이유로 골라도 출발지를 모르면 다른 공원까지 멀다고 추론하지 않는다. 해당 장소만 제외하고, 사용자가 후보 범위를 더 고칠 수 있게 한다. 제외 목록과 복원 동작을 표시한다. 이미 고정한 장소를 제외하려는 경우 충돌을 알리고 무엇을 바꿀지 사용자가 선택하게 한다.

이는 추천을 본 뒤 알게 된 자신의 조건을 반영하는 작은 기능이다. 기존 ‘갈 수 있는 공원’ 선택의 지름길로 구현할 수 있다. 핵심 흐름과 사용자 검증 시간을 확보한 뒤에만 더한다.

## 9. 9월 18일 완성을 위한 우선순위

일반 Place 구조는 처음부터 적용하고, 기능 순서는 다음을 권한다.

1. **한강 5곳 핵심 완성:** 실제 데이터, AI 조건 해석, 기준 계획 비교, 고정·해제, 공개 URL.
2. **갈 수 있는 공원 범위:** 선택한 장소 안에서만 비교.
3. **같은 5곳의 목적지 미정 진입:** 같은 화면·엔진을 쓰며 원래 계획 없는 상태를 정확히 처리.
4. **선택 완료와 검증:** 계획 문구 복사·지도 연결, 실제 사용자 관찰, 제출 자료.
5. **여유가 있을 때만 장소 확장:** 활동·환경이 맞는 새 그룹을 정의하고 검증된 후보부터 추가.
6. **이후 실제 경로와 이동 부담:** 그 뒤에 시간대 평균 교통 혼잡을 별도 정보로 검토.

9/18 13시까지 첫 단계의 공개 흐름이 통과하지 못하면 새 장소·활동 그룹 공개를 시작하지 않는다. 목적지 미정 진입도 핵심 비교·배포를 지연시키면 다음으로 미룬다. 오후 사용자 관찰과 16~18시 제출 작업은 확장 기능 때문에 없애지 않는다. 추가 장소의 숫자는 납품 약속으로 잡지 않는다.

## 10. 수상 관점에서 보여줄 증거

두 진입을 다음처럼 시연할 수 있다. 실제 예측 차이가 없으면 다른 결과를 연출하지 않고 조건 준수 자체를 보여준다.

- 목적지 미정: “19시 이후, 여의도나 망원에서 산책” → 실제 후보 → “망원은 이번에 제외” → 여의도 안에서 다시 비교.
- 목적지 있음: “17시 여의도, 18시까지 늦출 수 있음” → 원래 계획과 대안 → “17시 고정” → 허용 범위 안에서 재비교.

측정할 것은 추천을 받기까지 걸린 시간, 사용자가 정한 필수 조건의 누락 여부, 바뀐 점의 이해, 실제 갈 수 있는 선택인지다. 목적지 미정 지원이나 장소 모델 일반화만으로 AI가 더 필요해졌다고 주장하지 않는다. **자연어의 여러 조건과 정정을 제대로 반영했는지**를 확인해야 한다.

이 보완안의 우선 제안은 **일반 Place 구조 + 한강 5곳 + 갈 수 있는 범위 + 한 화면의 두 시작 방식**이다. 서울 전체 확장은 이 흐름이 작동하고 쓰임을 확인한 다음 단계로 둔다.
