# 숨맵 — Wanted AI Championship 제출 기획안

작성·개정: 2026-09-17 · 버전: 2 — 제품 UX와 최소 변경 재계획 반영 · 상태: 구현 전 기획 · 내부 완성 목표: 2026-09-18 18:00 KST

사용자가 확인한 조건은 ‘아직 아이디어 단계’와 ‘9월 19일 유럽 출발’이다. 팀 규모는 미확정이므로 1인 개발과 AI 개발 도구 보조를 기준으로 작성했다. 이 문서의 기능·일정·품질 기준은 제안이며, API 연동·개발·배포를 완료했다는 의미가 아니다.

[검토한 원안 대화](https://chatgpt.com/share/6aab58cd-3634-83ee-bbf4-c95f4f84aca2)를 바탕으로 공식 데이터·대회 조건을 확인하고 범위를 재설계했다.

## 1. 제품 결정

**숨맵: 붐비는 곳을 피하고 싶은 사람을 위한 AI 외출 플래너.**

사용자가 가려던 외출의 목적을 유지하면서, **원래 계획을 가능한 한 적게 바꾸고 혼잡을 줄이는 방법**을 찾는다. 장소와 시간을 변경할 때 얻는 이점과 감수할 변화를 함께 보여준다. 첫 버전은 서울 한강공원 5곳의 산책으로 한정한다.

- 첫 사용자: 한강 산책을 계획하면서 혼잡을 피하고 싶은 서울 생활자.
- 문제: 현재 혼잡도만 보면 내가 도착할 때의 상황과 대안을 각각 찾아 비교해야 한다.
- 핵심 결과: ‘선택한 장소·시간에 가기 / 같은 시간에 다른 장소 가기 / 같은 장소에 다른 시간 가기’ 중 근거 있는 선택.
- 제품 형태: 모바일 중심 반응형 웹 + 기본 PWA. URL로 즉시 체험하며, 지원 기기에서는 홈 화면에 추가할 수 있다.
- 대표 체험: **말로 계획한다 → 해석된 조건을 확인한다 → 선택지를 비교한다 → 내 사정에 맞게 고친다.**
- 첫 화면 문구: **오늘은, 덜 붐비는 쪽으로.**
- 이름의 의미: ‘숨 돌릴 공간을 찾는다’는 브랜드 표현. 소음, 좌석 여유, 감각적 편안함을 측정하거나 보장하는 서비스로 설명하지 않는다.

주력 화면은 추천 결과이고, 지도는 위치와 집계 범위를 이해하는 보조 수단이다. 건물 모델·입자 효과보다 선택지가 달라지는 이유를 쉽게 보여주는 데 시간을 쓴다.

## 3. 기존 아이디어에서 유지·수정할 점

사용자의 출발점, 개인 선호를 반영한 추천, 혼잡 배경 설명, 시간별 데이터 축적이라는 방향은 유지한다. 다만 이번 제출 범위와 장기 비전을 분리한다.

## 4. 9월 18일 제출 버전

대상 후보는 여의도·반포·뚝섬·망원·난지한강공원이다. **아직 실제 API 응답을 검사하지 않았으므로 확정 목록은 아니다.** 개발 첫 단계에서 공식 장소코드·집계 경계·현재 데이터·예측 제공 여부를 확인해 5곳을 확정한다. 한강 산책이라는 공통 목적을 유지할 수 있는 후보를 우선한다.

### 제출 목표 기능

| 기능 | 구체 동작 | 완료 조건 |
|---|---|---|
| 첫 요청 | 자연어 또는 완성된 예시 요청으로 시작 | 가입·위치 권한 없이 시작 가능 |
| 조건 해석 | 원래 장소·시각·체류시간, 반드시 지킬 조건과 선호 구분 | 확인·수정 가능한 요약, 임의의 변경 허용 없음 |
| 현재 상태 | 5곳의 혼잡 단계·집계 시각·집계 범위 표시 | 실제 데이터와 출처 표시 |
| 최소 변경 비교 | 추천 1개·다른 대안 최대 1개·원래 계획을 중복 없이 표시 | 변경 내역과 절충점 표시, 총 3개 이내 |
| AI 설명 | 추천 이유와 다른 후보를 고르지 않은 이유 | 후보 ID·근거 ID 검증, 없는 수치 생성 금지 |
| 조건 수정 | 시간·장소 고정/해제, ‘덜 붐빔 우선’ 전환 | 원래 계획 기준 유지, 수정한 조건 준수 |
| 예측 그래프 | 선택 시간 전후 우선, 제공 범위 최대 12시간 펼치기 | 원자료 시각·예측 시각·결측 표시 |
| 지도 | 모바일 펼치기, 데스크톱 지도·플래너 분할 | 지도 없이도 요청·비교·재추천 사용 가능 |
| 기본 PWA | manifest·아이콘·독립 창 모드·모바일 안전 영역 | HTTPS와 지원 브라우저에서 홈 화면 실행 확인 |
| 공개 운영 | 모바일 대응, 캐시, 오류·오래된 데이터 상태 | 공개 URL에서 전체 흐름 실행 |

기존 최소안에서 예측 그래프·지도·기본 PWA까지 제출 목표로 올린다. 첫 배포와 재추천 흐름을 먼저 통과시킨 뒤 병렬로 붙인다. 계정·데이터·모바일 문제로 일정이 밀리면 아래 축소 순서를 적용한다. 고성능 개발 AI를 사용할 수 있다는 이유만으로 외부 연동과 검증 시간을 줄여 잡지는 않는다.

### 조건부 완성도 개선

- 통합 API에서 바로 얻을 수 있는 주변 행사 카드: 행사명·기간·출처. 일정이 확인되지 않으면 표시하지 않는다.
- 국문 통합 API에 있는 기온·강수·미세먼지 참고 카드. 미래 계획의 필터로 쓰려면 해당 미래 시각 자료가 별도로 확인되어야 한다.
- 3D 건물: 기존 벡터 타일의 건물 높이를 이용하고, 서울 타일·라이선스·성능이 확인될 때만 적용한다. 별도 도시 모델을 제작하지 않는다.
- 변경된 결과의 짧은 전환 효과와 대표 이미지. 움직임 감소 설정을 존중한다.

이번 제출에는 로그인, 푸시 알림, 전국 검색, 실시간 웹/SNS 탐색, 자체 혼잡 예측, OD 애니메이션, 정밀 3D, 다중 경로 탐색을 포함하지 않는다.

## 5. 대표 사용자 여정과 화면

예시 요청: **“오늘 오후 5시에 여의도한강공원에서 한 시간 걷고 싶어. 붐비는 건 싫고 한 시간 늦게 가도 돼. 다른 한강공원도 괜찮아.”**

1. 해석한 조건을 표시한다: 한강 산책 / 원래 도착 17시 / 체류 60분 / 허용 도착 17~18시 / 다른 한강공원 가능 / 혼잡 회피 선호.
2. 같은 데이터 묶음으로 원래 계획과 두 종류의 대안을 비교한다.
3. 추천을 하나 강조하고, 그 추천을 선택하면 포기하는 조건을 같이 쓴다.
4. 사용자가 ‘시간은 유지’를 선택하면 17시 후보만 남기고 다시 추천한다.
5. 선택한 장소의 원자료 시각·예측 여부·출처를 열어 볼 수 있다.

아래는 **설명용 가상 상태**이며 현재 공원 정보가 아니다.

| 선택지 | 장소·시간 | 혼잡 정보 | 바뀌는 조건 |
|---|---|---|---|
| 원래 계획 | A공원 17시 | 약간 붐빔 예측 | 없음 |
| 장소 변경 | B공원 17시 | 보통 예측 | 목적지 변경, 이동시간 미산정 |
| 시간 변경 | A공원 18시 | 보통 예측 | 도착 1시간 지연 |

“A공원을 유지하려면 18시 방문을 고려해 보세요. 제공된 예측에서는 17시보다 혼잡 단계가 낮습니다.”처럼 설명한다. ‘시간 유지’로 바꾸면 B공원 대안이 남는다. 실제 데이터에 차이가 없다면 차이가 없다고 알려주며, 연출을 위해 추천을 강제로 바꾸지 않는다.

한 페이지의 구성은 다음과 같다.

- 상단: 서비스 목적, 한 줄 입력, 바로 체험할 예시 요청.
- 조건 줄: 목표 장소·도착 시각·혼잡 회피 정도·변경 가능한 조건.
- 본문: 추천 1개, 다른 대안 최대 1개, 원래 계획. 같은 선택은 중복 카드로 만들지 않는다.
- 보조 영역: 장소 지도 또는 장소 목록, 선택 시 상세 패널.
- 근거 영역: 집계 시각, 예측 시각, 출처, 관련 행사, 데이터 제한.

모바일에서는 추천 결과를 먼저 보여주고 지도를 접을 수 있게 한다. 장소 데이터가 없으면 ‘미제공’으로 표시하고 ‘여유’로 채우지 않는다.

## 5-1. 제품 형태와 UX 원칙

### 제품 형태와 배포

**첫 제출은 Next.js 기반 모바일 중심 반응형 웹 + 기본 PWA로 한다.** 설치와 회원가입 없이 URL로 핵심 기능을 사용할 수 있다. PWA는 같은 웹에 홈 화면 실행 경험을 더하는 것이며, 별도의 하이브리드 앱을 동시에 개발하지 않는다.

| 선택 | 이번 결정 | 이유 |
|---|---|---|
| 반응형 웹 | 기본 제품 | 심사·공유·모바일 접속을 같은 URL로 처리 |
| 기본 PWA | 함께 적용 | 원하는 사용자가 홈 화면에 추가해 독립 창으로 실행 |
| Capacitor 하이브리드 앱 | 이후 검토 | 네이티브 기능 수요와 별도 빌드·스토어 작업이 생길 때 |
| 별도 네이티브 앱 | 이번 범위 밖 | 현재 핵심 체험은 웹으로 제공 가능 |

기본 PWA 범위는 `app/manifest.ts`, 이름·아이콘·시작 URL·`display: standalone`, 테마/배경 색, Apple 터치 아이콘과 모바일 safe area 대응이다. 설치 안내는 지원 브라우저에서만 적절히 표시하고, 첫 추천을 가로막지 않는다. iOS 등은 홈 화면 추가 방식이 다를 수 있으므로 실기기로 확인한다. 오프라인 추천·푸시·백그라운드 동기화는 포함하지 않는다. 설치 가능 여부와 오프라인 지원은 별개다. [Next.js PWA 가이드](https://nextjs.org/docs/app/guides/progressive-web-apps)

향후 Capacitor 적용 시에는 웹 UI·타입·추천 규칙을 재사용하되 웹 번들과 서버 API의 경계를 검토한다. Next.js의 서버 API·서버 전용 기능이 네이티브 번들 안에서 자동 실행된다고 가정하지 않는다. API 서버 운영과 네이티브 빌드·테스트·스토어 배포가 별도로 필요하다. [Capacitor 워크플로](https://capacitorjs.com/docs/basics/workflow)

### 경험의 원칙

1. **말로 시작하고 화면에서 조정한다.** 최초 입력은 자연어, 이후 변경은 조건 칩과 버튼이 기본이다. 채팅 기록을 계속 쌓는 화면은 만들지 않는다.
2. **원래 계획을 계속 보여준다.** 재추천을 몇 번 하더라도 비교의 기준 장소·시각·체류시간은 유지한다.
3. **변경 내용을 구체적으로 쓴다.** ‘장소 그대로 · 도착 1시간 늦춤’, ‘시간 그대로 · 여의도→망원’처럼 표현한다. 변경 점수나 기준이 불명확한 ‘조금/많이 변경’ 등급은 기본 화면에 쓰지 않는다.
4. **해석을 수정할 수 있게 한다.** AI가 읽은 조건과 기본값을 구분하고 사용자가 직접 고친다. ‘한 시간 늦게’는 0~60분 지연이며 ±60분이 아니다.
5. **사용자가 고정한 조건을 유지한다.** 더 한산한 후보가 있어도 시간·장소 고정을 임의로 해제하지 않는다.
6. **데이터와 설명을 분리한다.** 장소·시각·혼잡·날씨는 구조화 데이터로, AI는 이유와 절충점으로 표현한다.

### 한 페이지의 화면 상태

| 단계 | 사용자가 보는 내용 | 주 행동 |
|---|---|---|
| 시작 | 짧은 제품 설명, 입력창, 완성된 예시 요청 2~3개 | ‘계획 비교하기’ |
| 조건 확인 | 장소·도착·체류·바꿀 수 있는 조건 요약 | 칩 수정 또는 결과 확인 |
| 결과 | 추천·다른 선택·원래 계획, 변경 내역·근거 | 계획 선택 또는 조건 조정 |
| 재계획 | 고정된 조건과 갱신 중인 결과 | 시간/장소 고정·해제, 되돌리기 |
| 상세 | 선택 시각 주변 예측, 데이터 시각, 날씨·행사 참고 | 전체 예측 또는 지도 보기 |
| 선택 완료 | 확정한 장소·시각·체류시간과 기준 시각 | 다시 조정 또는 ‘새 계획’ |

원문이 충분히 명확하면 조건 요약과 결과를 같은 화면에 보여주어 확인 버튼을 한 번 더 누르게 하지 않는다. 오전/오후가 불명확하거나 시간 변경 허용 여부처럼 결과에 큰 영향을 주는 조건이 빠졌다면 해당 항목 하나만 선택하게 한다. ‘시간은 상관없어요’ 같은 불완전한 문장은 처음의 단독 예시보다 조건 수정 버튼으로 사용한다.

조건 잠금에는 대상 값을 쓴다: ‘17:00 고정’, ‘여의도 고정’. 기본값은 원래 계획이다. 대안의 값을 고정할 때는 ‘망원 고정’처럼 별도 선택해야 한다. ‘더 한산한 곳’은 선호 순서를 바꾸는 버튼이며 새 Hard Constraint가 아니다. 버튼을 누르면 기존 카드 공간에서 결과가 바뀌고, ‘17시를 유지해 다시 비교했어요’라는 짧은 설명을 보여준다. 선택 상태와 해제 방법도 표시한다.

‘이 계획 선택’은 현재 탭의 세션 상태에 보관하는 동작이다. 외부 예약·길찾기 실행·알림 설정을 의미하지 않는다. 완료 카드에서도 다시 조정할 수 있다. 로고는 입력을 지우지 않으며, 별도 ‘새 계획’ 버튼으로만 흐름을 초기화한다.

### 모바일과 데스크톱

| 화면 | 배치 | 상호작용 |
|---|---|---|
| 모바일 | 입력/조건 → 추천 → 빠른 수정 → 다른 선택·원래 계획 | 지도는 ‘지도에서 보기’로 펼침. 상세는 바텀시트 또는 펼침 영역 |
| 데스크톱 | 지도와 플래너 좌우 분할 | 같은 후보 선택·시간 필터가 양쪽에 동기화 |

모바일 키보드가 열려도 입력·실행 버튼이 가려지지 않게 한다. 상세를 닫으면 기존 카드와 스크롤 위치로 돌아간다. 색만으로 혼잡을 구분하지 않고 단계 이름을 함께 쓴다. 조건 잠금은 키보드로도 조작 가능하고, 결과 갱신은 보조 기술에 알린다. 모션 감소 설정에서는 카드 전환을 단순하게 한다.

### 시간 그래프와 지도

기본 그래프는 선택한 방문 시각 전후 약 2~3시간 중 실제로 제공되는 미래 구간이다. ‘전체 예측’에서 제공 범위 최대 12시간을 펼친다. **지금보다 과거인 부분은 과거 데이터가 없으면 비워 둔다.** 여유·보통·약간 붐빔·붐빔을 이산 단계로 표시하고, 임의의 매끄러운 곡선이나 중간 혼잡값을 만들지 않는다. 선택 시각과 체류 구간을 표시하되, 표본 사이 상태가 확인되지 않았다는 점을 유지한다.

현재 관측과 미래 예측은 표식·라벨로 구분하고 원자료 갱신 시각을 함께 표시한다. ‘18시 표본은 보통’이라는 정보를 ‘18시 이후 계속 한산’으로 바꾸지 않는다. 예측 누락은 그래프의 빈 구간으로 표시한다. 지도와 카드가 같은 데이터 스냅샷을 사용하도록 하고, 개별 장소의 서로 다른 원자료 시각은 유지한다.

3D는 MapLibre의 건물 높이 기반 extrusion을 활용할 수 있다. 공식 예제처럼 높이 속성이 있는 타일이 필요하며, 서울 다섯 공원을 한 화면에 보여주는 넓은 줌에서는 건물 표현 효과가 제한될 수 있다. 전체 지도는 가볍게 유지하고 선택 장소 확대 시에만 적용하는 것이 적절하다. 저사양 기기나 WebGL 오류에서는 2D 또는 카드로 전환한다. [MapLibre 공식 예제](https://maplibre.org/maplibre-gl-js/docs/examples/display-buildings-in-3d/)

### 오류와 빈 결과

| 상태 | 화면 동작 |
|---|---|
| 최초 AI 해석 실패 | 입력을 보존하고 장소·시각·변경 범위를 직접 선택하는 간단한 폼 제공 |
| AI 설명 실패 | 검증된 비교 결과를 유지하고 규칙 기반 문장 표시 |
| 조회·재계획 진행 중 | 이전 결과를 유지하되 ‘이전 조건의 결과’임을 표시, 선택 버튼 잠시 비활성화 |
| 고정 조건을 만족하는 후보 없음 | 고정을 유지하고 어떤 조건을 풀면 비교 가능한지 제안, 사용자 선택 후 변경 |
| 더 한산한 후보 없음 | 원래 계획과 비슷하거나 차이가 없다고 알림 |
| 예측 없음·체류 구간 자료 부족 | 현재/도착 시각 정보만 분리 표시하고 체류 전체를 평가한 것처럼 설명하지 않음 |
| 오래된 자료·서울 API 실패 | 마지막 정상값과 기준 시각 표시, 최신 추천 불가 시 명시 |
| 지도 실패 | 장소 카드·비교·조건 수정 유지 |
| 오프라인 | 연결 필요 안내, 저장된 예전 결과를 새로운 추천처럼 제시하지 않음 |

재계획 중 입력이 다시 바뀌면 최신 조건 버전의 응답만 반영한다. 늦게 도착한 이전 응답이 최신 카드를 덮어쓰면 안 된다. 조건 변경을 되돌릴 때는 이전 조건을 복원하되, 데이터가 낡았으면 새 데이터로 다시 계산한다.

## 6. AI와 일반 코드의 역할

**AI는 사용자의 말을 외출 조건으로 바꾸고, 근거 안에서 대안을 설명한다. 수치·시간·조건 충족 여부는 코드로 검증한다.**

```text
사용자 요청 → AI 조건 해석 → 사용자가 확인 가능한 조건
                                  ↓
서울시 현재·예측 → 서버 캐시 → 가능한 장소×시간 후보 계산
                                  ↓
                     추천 순위와 근거 묶음 생성
                                  ↓
                     AI 설명 → 서버 검증 → 결과 화면
```

권장 구현은 구조화 응답을 지원하는 LLM API 한 종류, 최대 두 단계 호출이다. 1단계는 조건 해석, 2단계는 확인된 후보를 설명한다. 조건 버튼으로 수정할 때는 이미 해석된 조건을 재사용해 비용과 지연을 줄인다.

### 조건 모델과 원래 계획

| 구분 | 저장할 내용 | 예시 |
|---|---|---|
| `originalPlan` | 사용자가 처음 요청한 장소·날짜·도착 시각·체류시간 | 여의도 / 오늘 17시 / 60분 |
| `hardConstraints` | 허용 장소, 도착 시각 경계, 장소·시간 고정 | 한강공원만, 17~18시 도착 |
| `softPreferences` | 선호 장소·시각, 허용 혼잡 단계, 추천 모드 | 여의도·17시 선호, 보통까지 허용 |
| `selectedPlan` | 현재 사용자가 선택한 후보 | 여의도 18시 |
| 버전 | 조건 버전과 참조 데이터 버전 | 이전 응답과 새 요청의 혼동 방지 |

‘한 시간 늦어도 됨’은 **선호 시각 17시 + 허용 구간 17~18시**다. 선호 시각은 Soft이고 허용 구간의 경계는 Hard다. ‘장소는 꼭 여의도’는 Hard, ‘사람 많은 건 싫어’는 Soft로 해석한다. 시간 변경이나 다른 장소 허용 여부를 말하지 않았다면 임의로 허용 처리하지 않는다. 결과에 필요한 경우 조건 요약에서 해당 허용 여부만 확인한다.

`originalPlan`은 재추천·후보 선택으로 덮어쓰지 않는다. 원래 요청의 해석 오류를 사용자가 수정하거나 명시적으로 ‘새 계획’을 시작할 때만 기준을 갱신한다. ‘17시 고정’ 해제는 사용자가 확인했던 허용 구간 17~18시를 복원하며 무제한 시간 탐색으로 바꾸지 않는다.

### 후보 생성과 최소 변경 규칙

1. 지원 장소와 실제 제공된 예측 시각으로 후보를 만든다. 날짜·시간은 KST, 이미 지난 도착 시각은 신규 추천에서 제외한다.
2. Hard 조건과 데이터 최신성을 먼저 검사한다. 필수 조건은 AI 설명이나 선호 변경으로 우회할 수 없다.
3. 기본 모드 **‘변경 최소’**에서는 허용 혼잡 단계에 들어오는 후보를 먼저 고른다. 그 안에서 `변경 항목 수 → 장소 유지 우선 → 시간 변경 분 수 → 혼잡 단계` 순으로 정렬한다.
4. 예를 들어 장소 변경과 1시간 지연이 모두 허용되고 혼잡도도 사용자의 허용 범위에 든다면, 한 항목만 바뀌는 후보 중 장소를 유지한 안을 먼저 제시한다. 이 순서는 제품의 기본 정책이며 검증된 인간 선호나 수학적 보편 최적해가 아니다.
5. **‘덜 붐빔 우선’** 모드에서는 같은 Hard 범위 안에서 `혼잡 단계 → 변경 항목 수 → 장소 유지 → 시간 변경 분 수` 순으로 정렬한다.
6. 허용 혼잡도를 만족하는 후보가 없으면 이를 알리고, Hard를 지키는 후보 중 상대적으로 낮은 혼잡도를 보여준다. Hard를 만족하는 후보 자체가 없으면 추천을 생성하지 않고 해제 가능한 조건을 제안한다.
7. 원래 계획이 선호를 이미 만족하거나 다른 후보가 실질적으로 낫지 않다면 그대로 유지할 수 있다. 같은 후보를 여러 카드로 반복하지 않는다.

변경 항목은 장소·도착 시각 두 가지로 한정한다. 체류시간은 사용자가 요청한 값을 유지하고 자동 축소하지 않는다. 화면에는 점수 대신 실제 차이만 표시한다. 내부적으로 이 차이를 Plan Delta라고 부를 수 있지만, 첫 버전에 ‘혼잡 비용+장소 비용+시간 비용+날씨 비용’의 임의 가중합은 도입하지 않는다.

혼잡 선호는 ‘여유만 선호 / 보통까지 괜찮음 / 약간 붐벼도 괜찮음’처럼 수정 가능하게 표시한다. 허용 단계는 개인의 선호이며 안전성 등급이 아니다. 장소별 혼잡 단계의 차이를 실제 사람 수나 마주칠 사람 수의 감소율로 환산하지 않는다.

### 도착·체류·날씨의 해석 범위

이번 추천은 **도착 시각의 제공 예측**을 기준으로 계산한다. 체류 60분은 계획 요약과 그래프 구간에 표시하지만 ‘60분 내내 한산하다’는 판정에는 사용하지 않는다. 이후 시각의 예측은 참고로 보여준다. 요청이 17:30인데 제공값이 17시·18시뿐이면 임의로 보간하거나 반올림하지 않고, 제공 시각 중 하나를 선택하게 한다. 시간 고정 상태에서는 사용자가 동의해야 바꿀 수 있다.

‘가까운 곳’, ‘30분 안에 도착’은 이동시간 검증이 필요하므로 이번 버전에서 충족했다고 주장하지 않는다. 대상 후보의 위치와 이동시간 미산정 상태를 보여준다.

날씨·대기는 기본적으로 참고 정보로 제공한다. ‘비 피하기’를 추천에 반영하는 확장은 해당 방문 시각의 예보가 실제로 있을 때만 활성화한다. ‘비는 절대 안 된다’고 요청해도 비가 오지 않는다고 보장할 수 없으므로 사용자가 고를 수 있는 예보 조건으로 설명한다. 현재 미세먼지를 미래 방문 시각의 대기질로 사용하지 않는다.

출력은 `recommended_option_id`, `alternative_option_ids`, `reason`, `tradeoff`, `evidence_ids`, `limitations` 정도로 제한한다. 서버는 모든 ID와 제약을 검증하고, 혼잡 단계·날짜·시각은 데이터에서 직접 렌더링한다. 존재하지 않는 장소, 행사, 예상 관객, 이동시간을 응답에 추가하지 못하게 한다.

설명 생성 실패 시에는 같은 후보를 규칙 기반 문장으로 보여주고 ‘AI 설명을 불러오지 못했어요’라고 표시한다. 최초 조건 해석이 실패해 후보를 계산할 수 없으면 간단한 수동 조건 폼으로 전환한다. 제출 전에는 실제 AI 호출을 통한 핵심 여정도 반드시 성공해야 한다.

인구 API는 한 번에 한 장소를 조회하며, sample 키 대상은 광화문·덕수궁으로 제한된다. 한강공원 서비스에는 인증키 발급과 실제 호출 확인이 먼저다. 예측은 응답의 제공 여부와 시간 배열을 확인한다. 대체 데이터 표시도 파싱해 정상 관측과 구분한다. [인구 API 명세](https://data.seoul.go.kr/dataList/OA-21778/A/1/datasetView.do)

서울시는 2025년 예측을 향후 12시간·120곳으로 확대했다고 공지했다. 현재 전체 대상 수와 다르므로 ‘121곳 모두 12시간 예측 가능’으로 일반화하지 않는다. 이번 UI는 실제 응답이 있는 가까운 시간만 선택 가능하게 한다. [서울시 예측 확대 공지](https://data.seoul.go.kr/together/notice/datasetNoticeView.do?bbsCd=10008&seq=27399e1302ead42db866fa14824c4c56)

날씨 명세는 서울시 영문 통합 API에서 교차 확인했다. 현재 영역에는 기온·강수·PM25/PM10와 `WEATHER_TIME`, 시간별 예보 `FCST24HOURS`에는 대상 시각 `FCST_DT`, 기온·강수유형·강수확률 등이 있다. 확인한 예보 목록에는 미래 PM25/PM10이 없다. 따라서 18시 추천에는 해당 날짜 18시의 강수예보를 사용하고 미세먼지는 현재 참고값으로 분리한다. `WEATHER_TIME`을 미세먼지의 개별 원천 관측시각이라고 단정하지 않는다. **국문 API의 동일 구조 여부와 실제 응답은 아직 검증하지 않았다.** [공식 영문 출력 명세](https://data.seoul.go.kr/dataList/OA-22714/F/1/datasetView.do)

### 추천 기술 구성

- 웹: Next.js + TypeScript, 반응형 웹 + 기본 PWA. 화면과 서버 API를 한 프로젝트에서 운영한다. [Route Handler 문서](https://nextjs.org/docs/app/getting-started/route-handlers)
- 저장: Supabase PostgreSQL 한 곳. 이번에는 최신 정상 데이터만 보관한다.
- 수집: **서버 공용 캐시가 5분 이상 오래됐을 때 요청을 계기로 갱신**하는 방식을 기본으로 한다. 같은 장소에 동시 요청이 들어와도 중복 갱신하지 않도록 한다. 접속이 없는 동안의 상시 수집은 보장하지 않는다.
- 수집 확장: 핵심 완성 후 Supabase Cron 같은 반복 작업에서 동일 수집 로직을 호출할 수 있다. 상시 이력 수집은 후속 범위다. [Supabase Cron](https://supabase.com/docs/guides/cron)
- 지도: MapLibre의 2D 표현을 기본으로 하고 사용 가능한 타일에 높이 속성이 있으면 선택 장소 확대 시 3D를 적용한다. 라이브러리와 지도 타일의 사용 조건을 각각 확인한다. [MapLibre 3D 예제](https://maplibre.org/maplibre-gl-js/docs/examples/display-buildings-in-3d/)
- AI: 사용할 수 있는 구조화 응답 지원 API 한 종류. 모델은 한국어 조건 해석 테스트 후 고정한다.
- 배포: 익숙한 호스팅에 공개 웹 URL 하나. 개발 도중 일찍 배포해 도메인·키·런타임 문제를 확인한다.

Vercel Hobby의 Cron은 하루 1회 제한이므로 5분 수집에 그대로 사용할 수 없다. 수집은 별도 스케줄러를 쓰거나 해당 주기를 지원하는 플랜을 확인해야 한다. [Vercel Cron 제한](https://vercel.com/docs/cron-jobs/usage-and-pricing)

5곳을 5분마다 하루 종일 수집하는 확장 구성은 **하루 1,440회**다. 이는 설계상 계산이며 API 허용량을 확인했다는 뜻은 아니다. 기본 구성도 실제 인증키 한도에 맞춰 캐시 만료 주기를 조정한다. 사용자가 접속할 때마다 서울시 API 5개를 새로 호출하지 않는다.

최소 구성은 정적 장소 목록 `places`와 최신 데이터 `latest_snapshots`다. 장소 ID·이름·공식 경계와, 원자료 시각·수집 시각·혼잡 단계·인구 범위·예측 목록·대체 여부를 보관한다. `snapshot_history`는 제출 이후 추가한다. 이때 같은 장소·원자료 시각의 응답은 중복 적재하지 않는다.

운영 정책 제안:

- 원자료 기준 15분 초과 데이터에는 지연 표시를 하고 적극적인 현재 추천에서 제외한다. 15분은 제품 정책 제안이며 공식 정확도 기준이 아니다.
- 원자료 장애 시 마지막 정상값과 실제 시각을 보여준다. 보관값을 최신 값으로 표시하지 않는다.
- 계획을 오래 열어 두었다가 다시 활성화하면 데이터 유효성과 이미 지난 도착 시각을 검사한다. 갱신으로 추천이 달라져도 사용자가 선택한 계획을 조용히 바꾸지 않는다.
- 후보가 부족하면 비교 카드를 줄인다. 모든 데이터가 오래되면 ‘현재 추천 불가’를 허용한다.
- 행사명·일정이 있어도 ‘혼잡 원인 확정’으로 쓰지 않는다. 행사 종료 시각만으로 혼잡 완화 시점을 만들지 않는다.
- 지도 로딩이 실패해도 장소 카드와 추천은 사용할 수 있게 한다.
- API 키는 서버에 보관한다. AI 요청에는 길이 제한·요청 제한·일일 사용량 상한을 두고 공통 설명을 캐시한다.
- 사용자의 원문·정밀 위치를 저장할 필요 없이 익명 체험으로 시작한다. 분석이 필요하면 최소 이벤트만 수집한다.
- 출국 후 개인 노트북이 꺼져도 수집·추천·배포가 작동하도록 한다. 호스팅 정지 조건과 사용량은 출국 전에 확인한다.

| 근거 | 반환된 모든 장소·예측·행사 참조가 실제 후보에 존재 |
| 미제공 | 예측 없음·오래된 정보·지원하지 않는 장소를 정직하게 처리 |
| 개인화 | 실제 선택 차이가 있는 입력에서 선호 변경이 순위나 결과를 바꿈 |
| 모바일 | 좁은 화면에서 입력·결과·조건 수정이 모두 가능 |
| PWA | 지원 기기의 홈 화면 추가·실행 확인, 설치 없이도 같은 기능 사용 가능 |
| 응답 순서 | 빠르게 조건을 연속 변경해도 마지막 조건의 결과만 화면에 반영 |
| 장애 | AI 실패, 공공 API 실패, 지도 실패를 각각 확인 |
| 사용자 이해 | 3명 내외가 1분 안에 선택·이유·변경 내역을 설명하고 실제 데이터와 AI 설명을 구분하는지 관찰 |
| 운영 | 노트북 종료와 무관하게 배포 서비스·수집이 유지 |

추천 품질 테스트는 자연어 요청 10~15개로 시작한다. 기본 요청뿐 아니라 금지 조건, 예측 범위 밖 시간, 알 수 없는 장소, 동률, 데이터 누락을 포함한다. 같은 평가 집합에서 ‘현재 혼잡도만 정렬’한 방식과 비교하면 AI가 어떤 조건을 더 잘 처리했는지 보여줄 수 있다. 사용자 효용이나 정확도 수치를 제출하려면 실제로 측정한 결과만 쓴다.

## 10. 추가 아이디어 우선순위

| 아이디어 | 사용자 가치 | 부담 | 권장 시점 |
|---|---|---|---|
| **장소 바꾸기 vs 시간 바꾸기** | 원래 하고 싶던 외출을 포기하지 않고 계획 수정 | 낮음~중간 | 이번 핵심 |
| **‘시간은 못 바꿔요’ 조건 수정** | AI가 내 사정을 이해하는 장면을 즉시 체험 | 낮음 | 이번 핵심 |
| 추천하지 않은 이유 | 더 한산해도 목적·시간에 맞지 않는 후보를 이해 | 낮음 | 이번 핵심 |
| 혼잡 배경 브리핑 | 주변 행사·공연과 현재 변화를 함께 이해 | 중간 | 이번에는 행사 카드까지만 |
| 도착 시간 중심 알림 | 출발 직전 계획을 다시 판단 | 중간 이상 | 이후, 알림 동의·운영 체계 필요 |
| 방문 후 ‘생각보다 붐볐어요’ 피드백 | 공공 지표와 사용자 체감 차이 검증 | 중간 | 제출 이후 |
| 개인별 반복 선호 | 몇 번의 선택을 통해 시간 변경·장소 변경 취향 학습 | 중간 | 피드백이 쌓인 이후 |
| 서울 타임머신 | 시간대별 도시 패턴 탐색 | 높음 | 별도 데이터 분석 기능 |

장기적으로는 5곳 → 공원·산책권역 → 문화 활동권역 순서로 늘린다. 카페 좌석이나 휠체어 접근성은 별도 데이터가 있어야 추가한다. 사업화는 향후 숙박·관광 서비스에 방문 시간 추천을 제공하는 방향을 검증할 수 있지만, 현재 구매 의사가 확인된 것은 아니다.

## 11. 제출 소개 초안

아래 문구는 개발 완료 후 실제 동작하는 기능에 맞춰 확정한다.

**서비스명**

숨맵 — 원래 계획을 덜 바꾸고, 덜 붐비게 외출하는 AI

**해결하려는 문제**

사람이 많은 곳을 피하고 싶어도, 현재 혼잡도만으로는 내가 도착할 시간의 상황과 다른 선택지를 비교하기 어렵습니다. 숨맵은 사용자가 원래 하려던 산책을 가능한 한 적게 바꾸면서 덜 붐비게 외출할 방법을 찾습니다. 모바일·데스크톱 웹에서 바로 체험하고, 지원 기기에서는 홈 화면에 추가할 수 있습니다.

**AI 활용 방식**

AI가 자연어에서 방문 목적, 반드시 지킬 조건, 바꿔도 되는 조건과 선호를 해석합니다. 서비스는 서울시 현재·예측 혼잡도에서 조건을 만족하는 후보를 계산하고, 혼잡 선호와 계획 변경 정도에 따라 비교합니다. AI는 추천·제외 이유와 절충점을 설명합니다. 사용자가 ‘17시 고정’처럼 조건을 바꾸면 원래 계획을 기억한 채 다시 비교하며, 결과에는 변경 내역과 근거 시각을 표시합니다.

**주요 AI 도구**

- 제품 내 AI: 실제 사용한 API 공급자·모델명, 조건 해석과 추천 설명 역할을 기재.
- 개발 과정 AI: 실제 사용한 개발 도구명과 기획·코드 작성·디버깅 등의 활용 방식을 기재.
- 혼잡 예측값의 출처는 서울시임을 명시. 자체 개발한 혼잡 예측 모델로 소개하지 않음.

**60초 시연 구성**

1. 0~10초: “한강에 가고 싶은데 붐비는 곳은 피하고 싶다”는 문제와 요청.
2. 10~25초: 원래 계획·장소 대안·시간 대안의 비교.
3. 25~40초: ‘시간 유지’를 선택해 추천이 재구성되는 장면.
4. 40~50초: 기준 시각·예측 출처·추천 근거 확인.
5. 50~60초: 실제 제공 범위와 다음 확장 방향.

시연 영상은 부가 자료다. 배포 서비스 자체에서 실제 AI 기능을 체험할 수 있어야 한다. 녹화·저장 예시는 촬영 또는 저장 시각을 표시해 현재 상황과 구분한다.
